# App-Generated Browser Hydration

[Runtime index](./index.md) · [Documentation index](../../index.md)

Zero's build/runtime generates an app-owned route manifest and browser entry.
The public hydration runtime consumes it; it does not scan route folders in the
browser or require application code inside the framework package. Normal apps
use the generated entry rather than calling hydration from each page.

## Advanced Public Surface

```ts
import {
  startHydration, type HydrationManifest, type HydrationManifestEntry,
} from '@zero/framework/react/hydrate-runtime';
```

startHydration(manifest) returns Promise<void>. A manifest contains routes and
serverRoutes. Each route entry supplies pattern, a page module load function and
ordered layout module load functions. Modules are app-owned; the page needs a
default component. serverRoutes lists patterns that require a full server request
instead of a browser-only module transition.

This advanced fragment assumes a manifest generated by the app build:

```ts
import { startHydration } from '@zero/framework/react/hydrate-runtime';
import { manifest } from './generated-route-manifest';

void startHydration(manifest);
```

The generated file is not a new discovery helper provided by this documentation.
Do not hand-copy a private framework scanner/renderer into an app to construct it.
See server [discovery](../../backend/runtime/discovery.md) and
[composition](../../backend/runtime/composition.md) for app-owned modules/build inputs.

## Startup

The runtime registers manifest routes, finds the DOM root with id=root and reads
the server route payload. It selects the entry by pattern, loads page/layout
modules and merges their route-auth requirements. Missing root, route payload,
entry or default page export emits its corresponding standard frontend hydration
code instead of inventing a route/page.

It wraps the shell in ErrorBoundary and RouterProvider. The root app layout
remains responsible for [AppProvider](./app-provider.md) and its client ownership;
hydration does not add a second client. SSR render mode uses hydrateRoot;
explicit client render mode uses createRoot. Initial params/loader data come
from the server-authored payload.

## Subsequent Navigation

For an ordinary browser route, the runtime loads its page/layout modules, updates
params and merged auth requirement, and renders without retaining old server
loader data as if it belonged to the new route. For a server route, or a current
route lacking a usable module, it reloads the browser's complete committed local
URL, preserving query and fragment.

Pending navigation is generation-scoped. A superseded module cannot overwrite
the newer page/params/auth requirement or redirect the newer URL. Completion after
unmount is ignored; a stale failure cannot clear a newer navigation's state.
Modules may finish loading/cache normally, but only the current mounted navigation
can commit presentation. This is not cancellation of an arbitrary provider/server
request or a new route execution authority.

The [authorization scope guard](./scope-transitions.md) independently prevents
SSR data or a protected subtree crossing identity/tenant replacement. Route module
ordering and authorization/data isolation are complementary boundaries.

## Failure And Verification

Startup failures use standard frontend hydration observability codes; render
failures reach ErrorBoundary. Do not expose raw credential/loader records in a
custom debug page or rewrite injected authorization metadata to make a route
appear valid. Build entries, server route payload and installed package must agree.

Focused synthetic browser regressions exercise the actual public startHydration
runtime with delayed modules, newer route params/auth requirements, query/hash
server fallback, stale missing-module fallback and unmount. Combined navigation
tests passed against working source; this is not yet installed-archive or complete
production SSR/bundle qualification.

The audited correction fixes races and URL loss without introducing a new route
language or changing app manifest file conventions. Applications normally keep
their existing generated entry; qualify their packaged build after upgrading.
