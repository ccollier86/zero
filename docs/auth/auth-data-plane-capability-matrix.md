# Auth And Data-Plane Capability Matrix

> Status: implementation inventory for the unreleased multi-tenant/RBAC
> candidate
>
> Last reviewed: 2026-09-28

This matrix names the security owner for every official Zero access-surface
family. It is the quick answer to four questions:

1. Which component makes the authorization decision?
2. Where does identity and tenant/application scope come from?
3. Which tests exercise the boundary?
4. Which lower-level API deliberately remains trusted application code?

“Implemented” below means the code and focused evidence exist in this tree. It
does **not** mean the candidate has passed the final release suite or has been
published. Follow the
[implementation checklist](./multi-tenant-auth-implementation-checklist.md)
and [release checklist](../releasing.md) before changing that status.

## Boundary rules

- The global `users.role` remains application/platform authority. It does not
  grant tenant data access in `multi` mode.
- A tenant ID from a path, header, query, body, hook argument, topic, or token
  claim is not authority. Managed surfaces rehydrate the current durable
  session and active membership, then derive the application/tenant scope.
- `single/simple`, `single/advanced`, `multi/simple`, and `multi/advanced` use
  the same `AuthorizationKernel`; simple and advanced profiles differ in how
  roles expand, not in whether enforcement is optional.
- UI gates and safe capability flags only narrow presentation. The server
  reauthorizes every read and mutation.
- Registered-resource field allow-lists protect Zero-managed CRUD, data-query,
  Sync, cache, and generated-form paths. They do not inspect direct SQL,
  unregistered tables, custom response bodies, or application-owned exports.
- `zero.unsafe`, direct database/SQL access, raw service instances, raw Elysia,
  and a directly composed `createSyncPlugin()` are explicit trusted-code
  surfaces. They do not inherit tenant safety by proximity to a managed route.

## Explicitly outside this candidate

These are not hidden runtime limitations or implied features. They are separate
capabilities that require their own design, implementation, and evidence:

- a protected, server-created Administration Organization and platform-tenant
  lifecycle/browser UI;
- upstream enterprise OIDC, SAML, SCIM, and group mapping;
- time-bound audited break-glass/support elevation;
- tenant-authored runtime custom roles (the current ceiling is app-declared
  static roles with durable assignments);
- external coordination for separate-database or cross-host replicas, including
  an ephemeral/presence topic bus (`file` mode already covers runtimes sharing
  one SQLite database for durable row changes and auth invalidation);
- automatic adoption/backfill tooling for a populated existing application;
- verified-domain autojoin, aliases/wildcards/subdomain inheritance, and direct
  tenant-to-tenant claim transfer; and
- per-tenant SQLite databases.

The current verified-domain release action is intentionally not “transfer.” It
retires the old claim, cancels derived pending admission, retains provenance,
and starts a seven-day cross-tenant quarantine. A later claimant must create a
new claim and complete the required proof.
